# Format: ### <name> | followed by content until the next ### or end of file

### plan_first
Before taking any action, output an execution plan in text with the following structure:

**Goal Analysis**: What does the goal require? What is the current screen state?
**Method Selection**: Which app to use? UI or shell? (toggles / brightness / airplane mode → shell priority; create / edit / delete → must go through app UI)
**Key Steps**: Roughly 3-5 step flow (e.g. observe → operate → verify → complete). Do NOT hardcode coordinates or package names.
**Verification**: How to confirm completion? (settings get / content query / ls / observe element check)
**State Check**: Is it possible the device state already satisfies the goal? (Update → already latest? Install → already installed? Toggle → already at target value? Navigate → already on target page?) Check first, then plan — if the goal is already achieved, the plan should be one shell verification + complete. Do not operate blindly.
**Anticipated Obstacles**: What might go wrong? (popups / onboarding pages / stale index / search needs enter key)

Output the plan and then immediately call tools to execute. Do not wait for confirmation.

### completion_signal
[System] You have executed multiple consecutive operations without checking if the goal is achieved.
- If the goal IS achieved → complete(success=true) immediately. Do NOT observe again.
- If the goal is NOT achieved but you are stuck → back() or home() to a clean state, then switch to a completely different approach. Staying on the same screen repeating actions will waste all remaining steps.
- If progress is being made → continue, but observe next to verify the state change.

### stagnation_warn
[System] WARNING — screen unchanged for multiple rounds. You appear to be stuck.
- If the goal state IS already achieved → verify once (shell get/check) then complete(success=true) immediately.
- If you have been using ONLY shell/debug commands → STOP. The shell cannot change the screen. IMMEDIATELY switch to UI: home() → find and tap the app icon on the current launcher → interact with the app directly.
- If launch() or am start didn't bring the app to foreground → home() → find the app icon on the launcher and tap it. Do NOT keep trying shell intents — tap the visible icon.
- If truly stuck with no clear next action → complete(success=false) with a specific reason.

### stagnation_force
[System — MANDATORY] The screen has been completely unchanged for multiple consecutive rounds.
You now have exactly TWO choices. Pick one. No other actions allowed:
1. If the goal is achieved → call complete(success=true) immediately (do NOT observe again to confirm)
2. If the goal is not achieved → you MUST switch to a completely different approach:
   a. Currently tapping elements → switch to tap coordinates, swipe, or back to retry
   b. Currently tapping coordinates → switch to tap_element for element targeting, or navigate_to
   c. Currently typing → check if the keyboard is shown, or switch to type_and_enter
   d. Currently waiting for load → proactively back() to the previous page and re-enter
   e. Currently only using shell/debug commands → STOP. The shell is not changing the screen. Switch to UI: observe → tap/find the app icon on the current screen → interact directly
   f. UI / search unresponsive → call shell(am start ...) to bypass UI with Intent (e.g. market://search?q=keyword)
   g. All of the above tried → complete(success=false), admit inability to finish
Forbidden: repeating the exact same action as the previous round. Forbidden: doing the same thing with a different tool (e.g. tap_element and tap on the same position count as the same action).

### degradation
[System] Element count dropped sharply (loading or page transition in progress). The screen is still changing — observe ONCE more to see the settled state. Do NOT wait (waiting causes an observe→wait→observe loop). If the next observe still shows very few elements, you are on a low-element screen where accessibility cannot expose state — switch to device-fact verification (see blind_zone guidance).

### blind_zone
[System] Screen has very few elements ({el}) persistently — a full-screen app (viewfinder / player / recorder) whose internal state the accessibility tree cannot expose. The count will NOT grow.
Do NOT keep re-observing, waiting, or querying `dumpsys activity` — the capture mode is NOT exposed there (querying only wastes steps).
- MODE: re-read the mode-switch button LABEL. It names the TARGET, not the current state ("Switch to Video Camera" = currently photo; "Switch to Camera" = currently video). If you just tapped a mode switch, observe ONCE to confirm the label flipped before pressing the main button.
- CAPTURE RESULT: verify via the file system — `shell(ls -lt /sdcard/Movies/ /sdcard/DCIM/Pictures/)`. `.mp4` under Movies = video recorded; `.jpg` under Pictures = photo taken.
Act on label + file facts, not on element count.
